A **Test Scenario** is a high-level description of what needs to be tested in a software application. It’s also called a **test condition** or **test possibility**. Instead of detailing exact steps, it focuses on **what to test**, often written from an end-user perspective.

### Key Points:

* **Why create Test Scenarios?**

  * Ensure complete test coverage.
  * Can be reviewed/approved by stakeholders.
  * Help estimate effort and prioritize work.
  * Identify important end-to-end transactions.

* **When not to create Test Scenarios?**

  * Application is unstable/too complex with limited time.
  * Agile projects (Scrum/Kanban) often skip them.
  * For regression or bug fixes where scenarios already exist.

* **Steps to Write Test Scenarios:**

  1. Read requirement documents (BRS, SRS, FRS).
  2. Identify user actions and technical aspects.
  3. List scenarios covering all features.
  4. Map scenarios to requirements using a Traceability Matrix.
  5. Review scenarios with supervisors/stakeholders.

* **Tips:**

  * Each scenario should link to at least one requirement.
  * Avoid mixing multiple requirements in a single scenario.
  * Don’t make scenarios overly complex.
  * Prioritize execution based on customer needs.

---

### Example Test Scenarios

**For eCommerce Application**

1. Check login functionality.
2. Check search functionality.
3. Check product description page.
4. Check payments functionality.
5. Check order history.
   (Other: homepage behavior, category pages, contact pages, daily deals, etc.)

**For Banking Application**

1. Check login and authentication.
2. Check money transfer.
3. Check account statement viewing.
4. Check fixed/recurring deposit creation.

---

✅ **Test Scenario = Broad functionality to test**
✅ **Test Case = Detailed steps + expected results**
