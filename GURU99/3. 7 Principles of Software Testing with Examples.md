✅ **7 Principles of Software Testing (with Examples)**

---

| **Principle**                             | **Explanation**                                                                 | **Example**                                                                                           |
| ----------------------------------------- | ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **1️⃣ Testing shows presence of defects** | Testing can show bugs exist — but can’t prove that bugs don’t exist.            | A login test finds invalid login is accepted — but passing tests don’t guarantee *all* bugs are gone. |
| **2️⃣ Exhaustive testing is impossible**  | You can’t test every input and path — choose risk-based and priority tests.     | Instead of testing all possible date formats, test common ones like `DD/MM/YYYY` and `MM/DD/YYYY`.    |
| **3️⃣ Early testing saves time and cost** | Start testing activities early in the SDLC to catch defects sooner.             | Reviewing requirements can catch missing scenarios before coding starts.                              |
| **4️⃣ Defect clustering**                 | A few modules contain most defects — focus testing efforts there.               | Payment module may have more bugs than static pages — test it more thoroughly.                        |
| **5️⃣ Pesticide paradox**                 | Repeating same tests won’t find new bugs — update tests regularly.              | Change test data or add new edge cases for login instead of always testing same valid credentials.    |
| **6️⃣ Testing is context dependent**      | Testing approach depends on the application type and domain.                    | Safety-critical software (medical devices) needs stricter testing than a blog website.                |
| **7️⃣ Absence-of-errors fallacy**         | Finding no bugs doesn’t mean the product is useful — it must meet requirements. | An app might have no functional bugs but fail if it doesn’t solve user needs (e.g., bad UX).          |
