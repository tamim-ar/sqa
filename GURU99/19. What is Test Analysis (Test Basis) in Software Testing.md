# 📘 What is Test Analysis (Test Basis) in Software Testing?

---

## 🔎 Definition

**Test Analysis** (also called **Test Basis**) is the process of examining and understanding test artifacts (requirements, design docs, etc.) to derive **test conditions** and test objectives. The goal is to gather what needs to be tested and form a foundation for creating test cases.

Common sources for test basis:

* SRS (Software Requirements Specification)
* BRS (Business Requirement Specification)
* Functional Design Documents
* The Application Under Test (AUT) and tester experience

---

## 🧭 Why Test Analysis Matters

* Converts requirements into concrete, testable conditions.
* Ensures coverage of functional and business expectations.
* Helps create meaningful test plans and test cases across SDLC phases.
* Enables traceability between requirements and tests.

---

## 🧪 Case Study — Example Requirement

> **Requirement:** Add search functionality to an eCommerce store

Even before the application is implemented, testers should analyze the requirement and derive test conditions. Example test conditions include:

### Example Test Conditions (not exhaustive)

1. Search with an **empty keyword** — behavior when user submits with no input.
2. Search for a **non-existent product** — behavior when no results match.
3. Search for a **keyword with multiple matches** — paging, sorting, results count.
4. Search with **special characters** (e.g., `!@#%`) — input sanitization / validation.
5. Search with **numeric-only** input (e.g., product codes).
6. Search with **case differences** (`Shirt` vs `shirt`) — case sensitivity.
7. Search with **leading/trailing spaces** — trimming behavior.
8. Search performance — response time under normal and peak loads.
9. Search result relevance — top results are most relevant.
10. Search suggestions / autocomplete behavior (if required).
11. Handling of **typos** — fuzzy match / spell-correction (if required).
12. Security checks — injection attempts in search input.
13. UI/UX checks — placeholder text, clear button, accessible labels.
14. Localization — search behavior for different locales / languages.

## 🔁 Test Analysis in the V-Model

In the V-Model, each development phase has corresponding test artifacts. Test analysis happens by inspecting documents available at each phase and deriving tests accordingly:

* **Requirements →** System/Acceptance test conditions
* **High-level design →** Integration test conditions
* **Low-level design →** Unit/test conditions for modules
* **Implementation →** Execute tests and record results

> The V-Model enforces building test design as early as possible, based directly on upstream artifacts.

---

## 🛠 How to Perform Test Analysis (Practical Steps)

1. **Collect test basis**: SRS/BRS, design docs, user stories, acceptance criteria.
2. **Read & highlight**: Mark functional and non-functional requirements.
3. **Identify ambiguities/gaps**: Note unclear or missing details for discussion with stakeholders.
4. **Derive test conditions**: Convert requirements into specific, testable conditions.
5. **Prioritize**: Rank conditions by risk, business impact, and frequency.
6. **Map to test cases**: For each condition, design one or more test cases.
7. **Traceability**: Link test cases back to requirements for coverage proof.
8. **Review**: Peer-review test conditions and cases with devs/product owners.
9. **Update**: Revise conditions as requirements/designs evolve.

---

## ✅ Test Analysis Checklist

* [ ] Have all requirement sources been gathered?
* [ ] Are ambiguous requirements flagged and clarified?
* [ ] Are both functional and non-functional conditions covered?
* [ ] Are test conditions traceable to requirements?
* [ ] Are edge cases and negative scenarios included?
* [ ] Is prioritization documented (High/Medium/Low)?
* [ ] Are performance and security requirements considered?
* [ ] Have stakeholders reviewed the derived conditions?

## 📝 Example: Derived Test Conditions → Test Case (Sample)

**Test Case ID:** TC_SEARCH_001
**Condition:** Search with empty keyword
**Pre-condition:** User is on the store search page
**Steps:**

1. Leave search input blank.
2. Click **Search** button.
   **Expected Result:** Appropriate message shown (e.g., “Please enter a search term”) OR search returns all items as per requirement.
   **Post-condition:** No unexpected server errors; request logged.

## 🧾 Summary

Test Analysis (Test Basis) is the essential early-activity that turns requirements and design artifacts into testable conditions. Good test analysis yields better test coverage, reduces miscommunication, and improves the overall quality of test planning and execution.
